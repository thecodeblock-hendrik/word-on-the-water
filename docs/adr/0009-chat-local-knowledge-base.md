# 0009. Got Questions chat from a local knowledge base

Status: accepted as scope on 2026-11-14 (nothing built yet; the plan is [chat.md](../archive/chat.md), PLAN.md step 1.10, mockups in [design/chat_mockups.html](../design/chat_mockups.html)).

## Context
The "New to faith? Start here" section needs a way for a newcomer to ask questions about the Christian faith and ask follow-ups. The first design used an LLM (OpenRouter, `nvidia/nemotron-3.5-super-vl:free`) with a web search tool limited to GotQuestions.org, Bible.org and BibleProject, under a strict system prompt.

Problems found:
- Faith questions are special personal information (POPIA) and special category data (GDPR). The free endpoint logs prompts and uses them to improve the provider's products, and a paid provider still needs a processor agreement and a cross-border transfer basis.
- Answers built from those three sites reproduce or closely paraphrase copyrighted text; South African fair dealing is narrow and the sites' terms may restrict automated use.
- A model can still hallucinate doctrine, leave its sources, or be steered by hostile text in retrieved pages. A disclaimer does not cure any of this.
- Cost, rate limits and outages of a third party in the request path.

## Decision
No AI model and no web search in v1. Answers come from our own reviewed knowledge base (`faith_kb.json`: 203 questions in 14 themes, 16 marked contested, 39 glossary terms), generated by `build_kb.py` from the original markdown source `Christian_Faith_Knowledge_Base.md`. The text is original, so we own it.

- **Retrieval:** in-process keyword scoring (BM25 style) over question, paraphrases, tags and answer text, with a near-exact question bonus and a confidence rule that also requires enough of the question's words to match. Low confidence returns the knowledge base's own no-answer text (a pastor referral); medium returns a "did you mean" list. No embeddings service, no database.
- **Follow-ups:** buttons that send knowledge base ids (read more, related questions, glossary terms) plus short free-text follow-ups resolved against the last entry shown.
- **History:** kept only in the visitor's browser (`sessionStorage`, gone when the tab closes, with a Clear chat button). The server is stateless: a request carries the new message plus `last_entry_id` and up to 20 `seen_entry_ids`, validated against the knowledge base. Nothing is stored or logged on the server.
- **Safety:** a deterministic crisis check runs first and returns the knowledge base's crisis text (South African numbers, plus a line for visitors elsewhere); messages containing personal details are rejected before use; rate limits per hashed address; `CHAT_ENABLED` is a kill switch and defaults to off.
- **No review gate (decided 2026-11-15):** a pastoral review of the knowledge base is not a launch requirement. The no-answer, crisis and contested replies point people to a local pastor.

## Consequences
- No new processor, cookie or third party; the privacy notice only gains a short chat section.
- Most LLM-specific threats (prompt injection, data leaving our systems, hallucination, cost) are gone. New risks are content correctness, matching quality and knowledge base tampering (mitigated by review, a committed JSON checked by `make kb-check`, and the evaluation set).
- The chat can only answer what the knowledge base contains and matches wording, not meaning. Quality is measured by an evaluation set built from the knowledge base's own 532 questions and paraphrases (a prototype found the right entry first 96.2% of the time and in the top three 99.6%, an optimistic figure because those words are in the index) plus off-topic, crisis, personal-detail and follow-up cases.
- A later LLM layer that only rephrases retrieved entries stays possible. It needs its own ADR, a paid zero-retention provider with a data processing agreement, and explicit consent first.
